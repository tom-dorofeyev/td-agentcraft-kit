# Feature Workflow

Use this workflow for any feature, non-trivial change, or anything introducing new abstractions.

## Purpose

Take a user request from vague intent to a working, reviewed, measurably clean, and acceptance-tested implementation. Two distinct phases: planning (with user), then AFK implementation.

## Entry Criteria

Use this workflow when:

- The task is a new feature or a non-trivial change.
- New abstractions, modules, or architectural decisions are required.
- The change spans multiple files or crosses layer boundaries.

Do NOT use for:
- Read-only questions (use the investigation workflow).
- ≤3 file, low-risk, isolated changes (use the Agent directly).

## Agent Sequence

```
1. Planner ──→ 2. Implementer
     │               │
     ▼               ▼
  PRD + Arch       Code-Review-Refactor Loop
  (user approved)  (AFK until acceptance tests pass)
```

## Phase 1 — Planner: Document Generation

The Planner collaborates with the user to produce two approved planning artifacts:

### 1a. Product Requirements Document (PRD)

Generated by delegating to the **product-specialist** subagent. Contains:
- **Epics** — high-level feature groupings
- **User Stories** — per-epic, actor-action-outcome format
- **Acceptance Tests** — Gherkin-style (`Given/When/Then`) per story

The PRD must be explicitly approved by the user before advancing.

### 1b. Architectural Design Document

Generated by delegating to the **architect** subagent, using the approved PRD. Contains:
- **High-Level Design** — system components and responsibilities (one sentence each), dependency direction, conceptual data flow. No code.
- **Low-Level Design** — plain-language contracts between components, key abstractions (concepts only), cross-boundary rules. Short and tight.

The architecture doc must be explicitly approved by the user before advancing.

**Output format:** For small scope, 2 documents. For large scope, 2 folders with structured markdown files. Decided collaboratively with the user.

### Phase 1 Gate

Both documents approved by the user. If the user says "implement it," hand off to the Implementer.

## Phase 2 — Implementer: AFK Loop

The Implementer takes the locked PRD and architecture document and runs autonomously. No user interruptions mid-loop.

### Implementation Loop

```
Builder ──→ Code Reviewer ──→ Refactorer ──→ Acceptance Tests
    ↑                                                    │
    └──────────────── (tests fail) ─────────────────────┘
                                │
                          all tests pass
                                │
                             DONE ✓
```

**Per-cycle sequence (strictly sequential):**

1. **Builder** — implement code per the architecture doc.
2. **Code Reviewer** — review against PRD, architecture, and quality standards. Output findings with severity.
3. **Refactorer** — run static analysis via `static-code-analysis`. Enforce all thresholds.
4. **Acceptance Tests** — run the Gherkin acceptance tests from the PRD. Every test must pass.

### Cycle Rules

| Cycle | Fix scope | Rationale |
|---|---|---|
| 1 | All findings + all metric violations | Full pass — clean baseline. |
| 2 | All findings + all metric violations | Second pass — eliminate noise. |
| 3 | Blocking + High + all metric violations | Tighten. Medium/low are known debt. |
| 4 | Blocking only + all metric violations | Prevent loops. |
| 5 | Blocking only + all metric violations | Final attempt. |

### Exit Conditions (all must be true)

- All Gherkin acceptance tests pass.
- No blocking review findings remain.
- All metric thresholds pass per `static-code-analysis` (complexity, duplication, coverage).

### Loop Cap

Maximum **5 cycles**. If blocking issues, metric violations, or test failures remain after cycle 5, escalate — do not loop further.

## Planner Responsibilities

- Receive the initial user request.
- Load `grill-me` if requirements are vague.
- Delegate to product-specialist for PRD. Get user approval.
- Delegate to architect for architecture doc. Get user approval.
- Hand off approved artifacts to Implementer.

## Implementer Responsibilities

- Run `preflight` before starting.
- Execute the implementation loop autonomously (AFK).
- Track cycle count and enforce fix scope tightening.
- Run acceptance tests after every cycle.
- Escalate at cycle 5 if gates still fail.
- Notify user via `notify` skill on completion.

## Escalation

Produce a structured escalation with:
- Which phase/cycle failed.
- Remaining blocking findings, metric violations, or test failures.
- What was attempted.
- Recommended next action.

Route back to the Planner if planning artifacts need revision. Otherwise, escalate to the user.
